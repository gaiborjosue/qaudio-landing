## Design

Monochrome, minimal user-facing copy, accessible semantics, keyboard interaction, and reduced-motion support. Preserve established animation and component behavior unless the task asks otherwise. Don't add motion/sound control buttons, a category selection arrow, or gratuitous copy.

Color is allowed only where it is already intentional:

- **Status cues:** visit section glass (yellow schedule change, green open, red closed); product condition badges and admin condition controls (green New, blue Demo, amber Used); admin news status dropdowns only (light green Published, pastel blue Scheduled, light gray Draft); faint green tint on the footer Send Message button; the product form's green check once a manufacturer page answers; the product form's Sale button in soft green while its sale is live; the header Connections popup's Instagram green check beside Sign out (keep icon and username there, apart from chat quick actions). The Connections icon shows a mini green check only when every configured service is connected, or an amber warning when any needs attention; a healthy account must never hide another's failure.
- **Photos:** grayscale, except the active item in a gallery (brand wall, repair carousel), shop product photos, QDeal images, and the Used Equipment service-bench photo. In the admin chat, Instagram previews and story designs show in color and mimic Instagram's colors (blue hashtags/mentions, red liked heart, blue active carousel dot).
- **Decorative:** Tune buttons' Halo color rim only while awaiting a response (New chat uses full Halo always); loader's chromatic edge streaks; copper cable divider in the contact footer; chat welcome emoji; chat send button's Chromatic spectrum. The Products tab's grid beam stays grey.

## Next.js conventions

Server Components by default; `"use client"` only on interactive pieces. Cache Components and Partial Prefetching are on.

- **Data:** read through `server-only` modules (`lib/*-data.ts`) as `"use cache"` functions with `cacheLife("content")` and a `cacheTag`. Use a short hard lifetime for public news queries with scheduled publication or expiration. No route segment `revalidate`/`dynamic` exports.
- **Dynamic reads:** `params`, `searchParams`, and `usePathname()` go inside `<Suspense>`. Read the signed-in user only through `sessionSupabase()` inside `<Suspense>` (it awaits `connection()`).
- **Hidden pages:** visited pages stay mounted but hidden (`<Activity>`). Client effects must clean up, avoid document-wide queries, and ignore zero-size measurements.
- **Route Handlers:** only for Client Components, the email callback (`/auth/confirm`), and the agent's bearer-authenticated cache callback (`/api/admin/revalidate`).
- **Mutations (including admin forms):** Server Actions that verify the signed-in admin inside every action (Proxy is only an optimistic redirect), validate input on the server, and write through the user's Supabase session so RLS applies (never the secret key). Then call `updateTag(<tag>)` (Route Handlers: `revalidateTag(<tag>, "max")`). The admin agent is the exception, below.
- **Images:** `loading="eager"` or `preload`, never `priority`.
- **Arc (uiarc) components** live in `components/arc` (registry `@uiarc`). Don't import Arc's global `foundation.css`; the wrapper scopes the monochrome tokens a component needs (see `sale-date-range.module.css`). Arc panels expand in place, so keep them out of the paint-contained chat rows.
- **CSP:** keep `next.config.ts` current when adding an external origin. Nonce-based CSP only on dynamic routes like `/admin`, set in `proxy.ts`.
- **Search/launch:** `lib/site.ts` fixes canonical URLs to `https://www.qaudio.com`; `lib/indexing.ts` keeps demo/preview and admin/internal responses `noindex`. Keep relative navigation, published-only sitemaps on catalog/news tags, and the crawlable news archive. Never switch live DNS before owner approval. Checks/runbook: `pnpm test:seo`, `pnpm check:launch`, `docs/launch.md`.
- Check new routes in `next dev` for Cache Components insights (overlay, console, or `get_errors` at `/_next/mcp`).

## Database

- Changes go through SQL migrations in `supabase/migrations`, saved as `<applied version>_<name>.sql` with exactly the SQL that was applied.
- Every table, view, or function the Data API can reach needs an explicit grant and RLS. Check access as each role and run the Supabase advisors after schema changes.
- Categories, brands, and products live only in Supabase, read through `lib/catalog-data.ts`; don't add code copies. Run `scripts/verify-catalog-access.sql` after catalog schema or policy changes.

Check the signed-in admin on every request; never accept a profile ID from the client. Zernio owns OAuth and tokens, so no Meta callbacks or local token storage. Return only allowlisted summaries and safe errors, never provider payloads or tokens. Test: `pnpm test:zernio`.
- **Google Business:** deferred `googlebusiness__` tools with their own admin check, approval previews, and selected-location guard. Website and Google hours use separate approvals; preserve unrelated special dates and reject stale revisions. No appointment-to-closed conversion. Live Google writes/uploads require exact `ZERNIO_GOOGLE_BUSINESS_WRITES_ENABLED=true` in any environment; diagnostics and development verification use GET only or mocks, never live writes. Standard text/one-photo posts only. Test: `pnpm test:google-business`.
- **Instagram publishing:** only through the agent's approved `instagram__` tools (`lib/admin/instagram-posts.ts`, `agent/lib/instagram.ts`). Zernio bypasses RLS, so each tool checks the admin itself (`instagramAccess`) and targets only accounts in the configured profile. Send an idempotency key per call, convert photos with sharp to the sRGB JPEG frame in `lib/admin/instagram.ts` (the preview mirrors it), upload via Zernio's presigned upload, schedule at most 7 days ahead. Photos only for now.
- **Story designs:** the only image generation. `design_story` (OpenRouter, `openai/gpt-image-2.6-flare`) and `edit_story` (`black-forest-labs/flux-3-image-klein`, never GPT Image for revisions); settings and prompt rules live in `lib/admin/story-images.ts`, framing in `agent/lib/story-frame.ts` (full-bleed 1080 × 1920 sRGB JPEG, one Klein extension at most for aspect fixes, never pad or crop). Paid steps verify the admin first and never throw, so nothing retries them. After each design or edit, show the image and cost receipts, then pause with `ctx.ask` for Continue or edit feedback (`agent/lib/story-review.ts`); Continue may pick an earlier version of the design (`lib/admin/story-versions.ts`), which the review returns as `design`, so posting always uses the returned design. Continue never approves publishing, and edits need a fresh post approval. Only for sale stories or stories the owner asks for, never feed posts. Rerun `scripts/brand-logo.mjs` when the logo changes. Test: `pnpm test:story`.
- **Tune prefill** (product manufacturer link check and page prefill, `lib/admin/product-page.ts`): server-only `TAVILY_API_KEY`, from Route Handlers that check the admin and same origin, and the agent's paid `products__read_manufacturer_page` (`agent/lib/product-page.ts`: verifies the admin first, never throws, stages photos in private chat uploads, returns usage receipts). It suggests, never saves; keep suggestions reviewable per field. Every server request to an admin-typed address goes through `lib/admin/public-fetch.ts` (https, public addresses only); never call `fetch` on such addresses directly. Test: `pnpm test:prefill`.

## Admin agent (`agent/`)

An eve project (pinned release candidate) hosted by Next.js through `withEve`. Read `node_modules/eve/docs/` before changing it.

- **Supabase:** only as the signed-in admin through `callerSupabase(ctx)`, so RLS applies. Never the secret key or the Supabase management MCP connector. Agent code can't import `server-only` modules; share pure code from `lib/` via relative imports.
- **Tool discovery:** domain tools use `deferred: true` with `hours__`, `products__`, `news__`, `deals__`, `instagram__`, or `googlebusiness__` names; teach discovery in the matching skill, no custom dispatcher. Keep current and historical write names in `lib/admin/tool-names.ts`. Run `node scripts/verify-agent-catalog.mjs` after changing the catalog, previews, or tool schemas.
- **Tool schemas:** eve rc.1 emits draft-07 but Anthropic needs 2020-12, so use fixed-length homogeneous arrays, not Zod tuples, in tool inputs.
- **Write tools:** each sets `approval` (`always()` with a prompt), takes a Zod schema from `lib/admin/schemas.ts`, is registered in `SAVE_TOOLS` (`lib/admin/tool-names.ts`) with a preview built from the site's own components in `components/admin/change-preview.tsx` (`instagram-preview.tsx` for Instagram; product changes use the read-only `product-review-table.tsx`; links `inert`), returns changed cache tags as `revalidate` (allowlisted in `lib/admin/site-cache.ts`), and exchanges dates as store-time `YYYY-MM-DDTHH:MM` (`lib/admin/store-time.ts`). Site writes return through `refreshAfterSave` (`agent/lib/site-cache.ts`); cache failures never repeat the write, and chat replay retries missed invalidations.
- **Approval cards** (`components/admin/approval-actions.tsx`): the agent proposes as soon as it has content; don't make it ask "save/publish/schedule/draft?" first, since the card is that question. A choice that differs from the proposal returns in a hidden `Approved as: {…}` line (`lib/admin/approval-choice.ts`). Card-sent messages must never be exactly `approve`, `deny`, `1`, or `2`. Answered cards say what happened (`lib/admin/card-heading.ts`). A write whose timing the owner should pick goes in that module's `FIELDS` and `releaseFields`.
- **Photos:** chat photos travel only as `Photo uploaded:` lines (`lib/admin/photo-lines.ts`), never eve attachments (`uploadPolicy: "disabled"`); the model sees them through the direct `view_photos` tool. No tool may use the session sandbox, so don't add attachments, `read_file`, bash, or other sandbox-backed features. Browser `<img>` loads of public Storage photos use `crossOrigin="anonymous"`. Test: `pnpm test:photos`.
- **Uploads:** chat photos and designs live in private `chat-uploads` (`uploads/chat/<session>/<uuid>`), registered via `lib/admin/media-lifecycle.ts`. Store paths, never signed URLs; preview through `/api/admin/media`. Saves copy used photos to public media with `placeUploads`. Cleanup is a Supabase Cron → Edge Function with its own credential, separate from the agent; delete through the Storage API only. Tests: `pnpm test:media`, `scripts/verify-media-access.sql`.
- **Deals:** `deals.kind` is `qdeal` (Q Audio-only offers on `/qdeal`, above its advice text) or `sale` (featured sales on `/sales`, above every published product with a live time-limited sale; `lib/deals.ts`). The product-sale flow adds a featured sale; its card's Don't feature denies with a hidden `Skip step:` note, which skips the step without disrupting the flow. Each deal has one optional image/flyer, text, optional product rows (new/demo/used, optionally linked to a shop product), or a combination. The Deals tab (`components/admin/deals-view.tsx`, `deal-editor.tsx`, `app/admin/deals/actions.ts`) and Tune's `deals__` tools save through `lib/admin/deal-save.ts`: the tab writes only the fields the owner changed and an open sheet rebases on newer saves; Tune's edits carry `updated_at` and refuse a changed deal. The chat's Create/Edit menus open deals in the tab, and its Edit with Tune sends `Item: deal <id>`. Approved uploads are copied into `deals/`; edits preserve an omitted image and remove it only with `image: null`. Preview private images through the authenticated media route. Tests: `pnpm test:deals`, `scripts/verify-deal-media-access.sql`.
- **Chat rendering:** follow the stream only while the agent works. Keep the thread memoized: pass cards the stable `ChatActions` (never the whole agent object), use stable props, and read usage only when Info opens. Costs use provider receipts, show missing data explicitly, and never substitute session-wide spend. The Create/Edit/Flows quick actions show only while the message field is empty, otherwise they fold into the composer's Quick actions tray (`components/admin/quick-menus.tsx`; keep its Enter guard). Test: `pnpm test:chat`.
- **Toasts:** Sileo (`sileo`, sharing the app's Motion via a pnpm override), monochrome, fired only through `components/admin/admin-toast.ts` and drawn by `AdminToaster` in the shell (focus holds a toast, Escape closes it). One at a time: chat news at the lower right from 1400px (`place: "chat"`), everything else at the top center under the header. Use them for news the owner can't see from where they are (Tune finishing or waiting while another tab is open, story progress, connection problems, a prefill answer scrolled away) and the tabs' short save/delete confirmations. Field errors, dialogs, and approval cards stay in place, and a toast's button only navigates, never approves. Chat toasts read the conversation in `lib/admin/chat-notices.ts` and skip a reopened chat's history. Test: `pnpm test:chat`.
- **Generative UI lists:** a reply's 3+ comparable things go through the direct `show_list` tool (`lib/admin/show-list.ts`, drawn by `components/admin/item-list.tsx`). Keep its rows domain-agnostic (title, detail, value/was, tags, site `href`); the client enriches known pages from data it already has, and the model gets back only "Shown.".
- **Local chat history:** New chat and new-session creation prune local Eve history to three ended conversations, keeping their child runs together and preserving all unfinished conversations. The admin-checked action runs cleanup after its response; only local development and the pinned local Workflow World layout are supported. Production storage and Supabase uploads are untouched. Test: `pnpm test:chat`.
- **Current chat:** `admin_chat_sessions` stores only each admin/environment's Eve ID and revision. `/admin` resumes it; first-message hooks claim it as the caller, and New chat rotates the revision after retirement. Failed history loads open a blank chat and clear only the matching pointer, without replaying input. `ADMIN_CHAT_ENVIRONMENT` overrides the automatic local/preview/production namespace and must match on Next and Eve. Tests: `pnpm test:chat`, `scripts/verify-current-chat-access.sql`.
- **Products: the Products tab and Tune share the writes; Metadata is a direct editor.** Products (`components/admin/products-view.tsx`) and categories/brands (`components/admin/metadata-view.tsx`, `app/admin/metadata/actions.ts`) save through Server Actions with admin checks and RLS. Tune adds and changes products with `products__create_product` and `products__update_products` through the same `lib/admin/product-save.ts` (changes as columns in `lib/admin/product-changes.ts`, cards in `components/admin/product-change-preview.tsx`), reorders, and sets or ends sales (`products__save_sale`, `products__end_sale`, `lib/admin/sale.ts`). Product writes are patches: Tune's only on products unchanged since it read their `updated_at`, the sheet only the fields the owner changed, and an open sheet rebases on newer saves. Deleting products and categories/brands stay in the tabs, never agent tools. Sales live in the `sale_*` columns and are priced only inside their window (`sellingPrice` in `lib/catalog.ts`); sale tools never touch `price_cents` or `msrp_cents`, and a discount is always a sale, never a regular price change. Don't add jobs that write as the admin later. Metadata keeps fixed slugs and the protected `used-equipment` entry, deletes only unused entries, and resolves artwork through `lib/catalog-assets.ts`. The shell (`components/admin/admin-shell.tsx`) keeps all tabs mounted and sets the URL with `History.prototype.replaceState`. Tests: `pnpm test:products`, `pnpm test:metadata`, `scripts/verify-metadata-access.sql`.
- **News tab:** a direct editor like Products, listing drafts and scheduled posts. Its sheet (`components/admin/news-editor.tsx`, Markdown body via `lib/admin/news-editor.ts`), row status quick edits, and delete save through admin-checked Server Actions (`app/admin/news/actions.ts`) and the same `lib/admin/news-save.ts` the agent's `news__` tools use; `/api/admin/news` loads one post for the sheet. Sale posts expire from public reads at their cutoff or when their last linked public sale ends. The Product sale flow links its approved prices to the saved post and uses its approved publication time. Post deletion offers to keep or cancel those future prices in one transaction. Edit with Tune is optional: it switches to the mounted chat and sends the exact `Item: news_post <id>`, where writes still need approval cards. Test: `pnpm test:news`.
- **Flows:** preset sequences live only in `lib/admin/flows.ts`; don't hard-code them in skills or prompts. Any sale, discount, or promotion belongs to product-sale; news-instagram is for news that isn't about one. Steps stay ordinary tool calls with normal approval cards, and flows never nest. The stepper rail's `RAIL_QUERY` must match the `admin.module.css` media query. Test: `pnpm test:flows`.
- **Task checklist:** `update_plan` snapshots drive the Trace Queue. Count 3+ independent requests, including read-only questions, never flow steps. Sol's dynamic instruction and model middleware (`agent/lib/task-planning.ts`) require a plan or applicable flow before domain work; successful outputs only, no approval bypass.
- **Models:** generation and Jev routing use OpenRouter in `agent/lib/models.ts`. Both Sol routes use Eve's local `chatgpt()` only with exact `DEBUG_DEV_MODE=true`, `EVE_DEV=1`, and a non-production process; surface auth failures with no paid-API fallback and never invent a USD receipt for subscription usage. Windows dev config prepares the process PATH with `scripts/dev-model-path.mjs`; never hard-code Codex version directories or change the global PATH. Per-turn OpenRouter Jev `auto`: 3+ requested non-flow tasks on Sol 6.2 medium, other changes and preset flows on Sol 6.2 low, simple read-only work on Muse Ember xhigh, Sol 6.2 low as fallback. Copywriting, compaction, card summaries, and product prefill share Ember xhigh.
- **Knowledge and memory:** domain rules go in `agent/skills/`; subagents only for bounded work that doesn't need the conversation. Memory (`agent/memory/supermemory.ts`) holds preferences, never site data; Supabase stays the source of truth.
