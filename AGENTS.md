## Working agreement

Read `AGENTS.md` and `README.md` before starting work. Keep product details in the README rather than duplicating them here.

- Inspect and safeguard existing uncommitted work; never reset or overwrite unrelated changes. Avoid concurrent writers to the same files.
- Maintain monochrome design (the only color is the faint green sent tint on the footer Send Message button; the visit section’s tinted glass is an intentional status cue: soft yellow for schedule changes, green for open, red for closed; photos are grayscale except the active item in a gallery, such as the brand wall or repair carousel, and shop product photos, which stay in color because the finish matters; the Used Equipment page’s service-bench photo also stays in color; the product details’ visual-condition badges are status cues: green for New, blue for Demo, amber for Used, and the admin product form’s and table’s condition controls use the same colors; the Products tab’s grid beam stays grey; the loader’s liquid glass keeps its chromatic edge streaks; the contact footer’s Kimber-style cable divider is copper; the admin chat’s welcome emoji is a native color glyph, and its circular send button uses the ReactDrops Chromatic Button’s spectrum material; the admin chat’s Instagram post preview shows photos in color, as they will be posted, and mimics Instagram’s own colors: blue hashtags and mentions, the red liked heart, and the blue active carousel dot), minimal user-facing copy, accessible semantics, keyboard interaction, and reduced-motion support. Preserve established animation and component behavior unless the task asks otherwise. Do not add motion/sound control buttons, a category selection arrow, or gratuitous copy.
- Follow the installed Next.js documentation rule above and use proportionate validation. Keep `pnpm lint` and `pnpm typecheck` error-free. Leave visual verification to the user; do not use the computer-use skill to verify changes.
- The Instagram connection's green check is an intentional connected-status cue, and so is the product form's green check once a manufacturer page answers.
- Next.js conventions: Server Components by default, with `"use client"` only on interactive pieces. Cache Components and Partial Prefetching are on:
  - **Data:** Server Components read data directly through `server-only` modules (`lib/*-data.ts`) as `"use cache"` functions with `cacheLife("content")` and a `cacheTag`. There are no route segment `revalidate`/`dynamic` exports.
  - **URL data:** read `params`, `searchParams`, and `usePathname()` inside `<Suspense>`.
  - **Session data:** read the signed-in user only through `sessionSupabase()` inside `<Suspense>`; it awaits `connection()`, because Supabase reads the clock and that can't run while Next prerenders or prefetches.
  - **Hidden pages:** visited pages stay mounted but hidden (`<Activity>`), so client effects must clean up, avoid document-wide queries that could match a hidden page, and ignore zero-size measurements.
  - **Route Handlers:** they serve Client Components, plus the email callback (`/auth/confirm`).
  - **Mutations:** these include admin forms. They are Server Actions that verify the signed-in admin inside every action (Proxy is only an optimistic redirect), validate input on the server, and write through the user’s Supabase session so RLS applies (never the secret key). Afterward they call `updateTag(<tag>)` (from a Route Handler, `revalidateTag(<tag>, "max")`). The admin agent is the exception: see below.
  - **Images:** use `loading="eager"` or `preload`, never the deprecated `priority`.
  - **CSP:** keep the `next.config.ts` Content-Security-Policy current when adding an external origin. A nonce-based CSP belongs only on dynamically rendered routes such as `/admin`, set in `proxy.ts`.
  - **Checking:** check new routes in `next dev` for Cache Components insights (dev overlay, console, or `get_errors` at `/_next/mcp`).
- Database changes go through SQL migrations in `supabase/migrations`, saved as `<applied version>_<name>.sql` with exactly the SQL that was applied. Give every table, view, or function the Data API can reach an explicit grant and RLS; check access as each role and run the Supabase advisors after schema changes. Shop categories, brands, and products live only in Supabase, read through `lib/catalog-data.ts`; don't add code copies, and run `scripts/verify-catalog-access.sql` after catalog schema or policy changes. Keep secret keys out of `NEXT_PUBLIC_` variables, commits, and chat.
- Social connections use the server-only Zernio SDK and a server-configured business profile (`ZERNIO_API_KEY`, `ZERNIO_PROFILE_ID`), shared by this site's admins. Check the signed-in admin on every integration request; never accept a profile ID from the client. Zernio owns social OAuth and tokens: do not recreate Meta callbacks or local social-token storage. Return only allowlisted account summaries and safe errors, never provider payloads, credentials, or tokens to the browser, agent, memory, or logs. Run `pnpm test:zernio` after changing the integration.
  - **Instagram publishing** goes only through the agent's approved `instagram__` tools (`lib/admin/instagram-posts.ts`, `agent/lib/instagram.ts`). Zernio calls bypass RLS, so each tool checks the signed-in admin itself (`instagramAccess`). Target only accounts listed in the configured profile, and refuse to change posts that target anything else. Send an idempotency key per tool call, convert photos with sharp to the fitted sRGB JPEG frame in `lib/admin/instagram.ts` (which the preview mirrors), upload them through Zernio's presigned upload, and schedule at most 7 days ahead. Store Tune's own record in the post's `metadata.tune`. A carousel's photo order arranged on its card goes back to the agent in an `Approved photo order:` line; the chat approves only the exact re-proposal (`lib/admin/instagram-arrange.ts`, tested in `pnpm test:zernio`), and anything else waits for the owner. Photos only so far; videos, comments, DMs, insights, and webhooks aren't wired.
- Prefill with Tune (the Products tab's manufacturer link check and page prefill, `lib/admin/product-page.ts`) uses the server-only `TAVILY_API_KEY` from Route Handlers that check the signed-in admin and same origin; it suggests, it never saves. Every server request to an address an admin typed goes through `lib/admin/public-fetch.ts` (https, public addresses only, checked at connect and after each redirect); don't call `fetch` on such addresses directly. Keep suggestions reviewable per field (accept/reject) and photos staged in `uploads/` as the admin. Return only safe errors, never Tavily or model payloads. Run `pnpm test:prefill` after changing it.
- The admin agent in `agent/` is an eve project (pinned release candidate) that Next.js hosts through `withEve`. Read the bundled docs in `node_modules/eve/docs/` before changing it.
  - **Supabase access:** agent code reaches Supabase only as the signed-in admin, through `callerSupabase(ctx)`, so RLS applies. Never use the secret key or the Supabase management MCP connector there. Agent code can't import `server-only` modules; share pure code from `lib/` (the agent's imports are relative).
  - **Domain discovery:** domain tools use `deferred: true` and canonical `hours__`, `products__`, `news__`, `deals__`, or `instagram__` names. Keep helpers, memory, and orchestration direct. Teach discovery/execution in the matching skill; do not add a custom dispatcher. Maintain current and historical write names in `lib/admin/tool-names.ts` for previews and scheduling; keep event/interaction ids unchanged. Run `node scripts/verify-agent-catalog.mjs` after changing catalog or preview routing.
  - **Write tools:** every write tool sets `approval` (`always()` with a prompt) and takes a Zod schema from `lib/admin/schemas.ts`. Add each one to the `SAVE_TOOLS` mapping in `lib/admin/tool-names.ts` with a preview drawn from the site's own components in `components/admin/change-preview.tsx` (Instagram posts use `instagram-preview.tsx`); make links in listings and cards `inert`. Return the cache tags it changes as `revalidate`, and allow them in `refreshSiteContent`. Tools exchange dates as store-time `YYYY-MM-DDTHH:MM` (`lib/admin/store-time.ts`). Pasted photos stage in `media/uploads/`, and a save copies the ones it uses into its section's folder with `placeUploads`.
  - **Products tab, not the agent:** products are added, edited, and deleted only in the admin workspace's Products tab (`components/admin/products-view.tsx`: a filterable table, a shadcn Sheet with the product form, and an Alert Dialog for delete). Its saves and deletes are Server Actions (see Mutations) sharing `lib/admin/product-save.ts`, and need no chat or AI turn. The agent only reads products and reorders them; don't give it product write or editor tools again. `products__save_product` and `products__delete_product` stay in `lib/admin/tool-names.ts` only so older chats render, and the chat's `HIDDEN_LINE` keeps the old `Product saved:`/`Products updated:`/`Editor:` lines hidden. The workspace shell (`components/admin/admin-shell.tsx`) keeps both tabs mounted and sets the address (`/admin`, `/admin/s/<session>`, `/admin/products`) with `History.prototype.replaceState`; a new direct editor for another domain would follow the same pattern.
  - **Knowledge and models:** put domain rules in `agent/skills/`, and use subagents only for bounded work that doesn't need the conversation. Generation models come from OpenRouter in `agent/lib/models.ts`; only the main chat's per-turn routing decision uses AI Gateway through `auto` from `eve/models`. Keep changes and complex workflows on Terra, simple read-only work on Haiku, and Terra as the routing-error fallback. Dynamic model options carry their own context budgets.
  - **Memory:** chats are disposable (New chat ends the session); `agent/memory/supermemory.ts` (via the eve 1.0 adapter in `agent/lib/supermemory.ts`) carries lasting preferences across them. Memory holds preferences and conventions, never site data: Supabase stays the source of truth, so don't teach the agent to answer hours, prices, or specs from memory. Don't re-enable the provider's `extract` or `read_document` tools without a plan for product photos.

## User-designated control chat

The original chat designated by the user is the control/orchestration room. For each new implementation task requested there, create a separate local project chat with scope, context, acceptance criteria, and documentation requirements. Monitor progress, review results, and report back to the user. Sequence tasks touching the same files to avoid concurrent writers.

Use lower reasoning for routine bounded tasks and higher reasoning only when complexity warrants it. Omit the `create_thread` model override and use the configured default unless the user requests a specific model. A user wanting a particular cheaper model can specify it or configure the default; do not invent prices or promise savings.

Implementation chats execute their assigned work without recursively creating chats. This workflow applies to the user-designated control chat and its dispatched work; it does not impose global spawning rules on arbitrary implementation chats.
